# NewLife.NovaDb 索引架构

> 对应模块：N02（主键索引）、N04（二级索引）、N05（冷热分离）
> 关联模块：S03（页读写）、S04（页缓存）

---

## 1. 概述

NovaDb 使用 **SkipList**（跳表）作为核心内存索引结构，配合冷热分离策略，在内存占用与访问性能之间取得平衡。索引以 `.nvi` 文件持久化，启动时按需加载。

---

## 2. 跳表（SkipList）

### 2.1 结构

概率性多层有序链表，O(log N) 查找/插入/删除：

```
Level 3: HEAD ──────────────────── 50 ───────────── NIL
Level 2: HEAD ── 10 ─────────── 50 ── 70 ────── NIL
Level 1: HEAD ── 5 ─ 10 ── 20 ─ 50 ── 60 ─ 70 ── 90 ── NIL
Level 0: HEAD ── 5 ─ 10 ── 20 ─ 30 ── 50 ── 60 ─ 70 ── 90 ── NIL
```

### 2.2 参数

| 参数 | 值 | 说明 |
|------|---|------|
| MaxLevel | 16 | 支持 2^16 节点高效查找 |
| P | 0.5 | 每节点 50% 概率升层 |

### 2.3 节点内容

节点存储索引键 + 行定位信息（`PageId + Offset`），多层指针用于快速查找与范围扫描。

### 2.4 复杂度

| 操作 | 平均 | 最坏 |
|------|------|------|
| 查找 | O(log N) | O(N) |
| 插入 | O(log N) | O(N) |
| 删除 | O(log N) | O(N) |
| 范围扫描 | O(log N + K) | O(N + K) |

### 2.5 选择 SkipList 的理由

- 实现简单，代码量远小于 B+ 树
- 天然有序，范围扫描友好
- 并发友好（可扩展为 lock-free）
- 适合内存索引场景

## 3. 冷热分离

### 3.1 架构

```
┌──────────────────────────────────┐
│ 热索引 (HotIndexManager)         │  ← 最近访问的数据段
│ 完整 SkipList 节点                │     O(log N) 查找
├──────────────────────────────────┤
│ 冷索引 (ColdIndexDirectory)       │  ← 长期未访问
│ 稀疏目录（每 N 行一个锚点）        │     查询时按需加载
└──────────────────────────────────┘
```

### 3.2 热索引管理器（HotIndexManager）

管理热段，将最近访问的数据段完整加载到内存跳表：

- **热数据窗口**：默认 600 秒（`HotWindowSeconds`），窗口内保持热索引
- **冷淘汰阈值**：默认 1800 秒（`ColdEvictionSeconds`），超过则卸载
- **热段最大行数**：默认 100 万行
- **LRU 淘汰**：按最后访问时间排序，超时自动降级

段元数据（`IndexSegment`）：段 ID、是否热段、键范围（MinKey/MaxKey）、行数、最后访问时间。

### 3.3 冷索引目录（ColdIndexDirectory）

长期未访问的数据段仅保留稀疏目录：

```
锚点 0: Key=1    → PageId=0,  Offset=0
锚点 1: Key=1001 → PageId=5,  Offset=128
锚点 2: Key=2001 → PageId=10, Offset=256
...
```

- **锚点间隔**：默认每 1000 行
- **查找流程**：二分搜索稀疏目录 → 定位锚点 → 从锚点页顺序扫描
- **访问提升**：频繁访问的冷段自动提升为热段

### 3.4 冷热访问流程

```
查询 key=5000:
  1. 热索引查找 → 未命中
  2. 冷索引二分搜索 → 锚点(key=4000, offset=1234)
  3. MMF 加载锚点后 1000 行
  4. 构建热索引段(key=4000~5000)
  5. 缓存到热索引管理器
  6. 返回 key=5000 数据
```

### 3.5 内存效果

| 场景 | 全量索引 | 冷热分离 | 节省 |
|------|---------|---------|------|
| 1000 万行，查最近 10 万行 | ~1.5GB | ~15MB | 99% |
| 1 亿行，查最近 100 万行 | ~15GB | ~150MB | 99% |

## 4. 索引文件（.nvi）

### 4.1 多索引多文件

每个索引独立文件，便于独立加载、淘汰与重建：

- 主键索引：`{Table}.nvi`
- 二级索引：`{Table}_{IndexName}.nvi`

### 4.2 文件结构

`.nvi` 存储持久化的"目录 + 块/页"结构，**不是内存跳表的镜像**。内存 SkipList 从 `.nvi` 按需重建热点区域。

```
┌────────────────────────┐
│  FileHeader (32B)       │  FileType=Index
├────────────────────────┤
│  目录区域                │  稀疏锚点 → 块偏移
├────────────────────────┤
│  索引页序列              │
│  Page 0: 索引条目        │
│  Page 1: 索引条目        │
│  ...                    │
└────────────────────────┘
```

### 4.3 加载策略

1. 引擎启动：仅读取 `.nvi` 稀疏目录锚点（冷索引）
2. 首次查询某范围：从 `.nvi` 加载对应块到内存跳表（热索引）
3. LRU 淘汰时：热索引卸载回冷索引稀疏目录

## 5. 二级索引（P1）

### 5.1 类型

| 类型 | 说明 |
|------|------|
| 普通索引 | 加速 WHERE 条件查询 |
| 唯一索引 | 加速查询 + 唯一性约束 |
| 联合索引 | 多列组合，最左前缀匹配 |

### 5.2 存储

每个二级索引独立 `.nvi` 文件，索引条目记录：`(索引键, 主键值)`。查询时先走二级索引定位主键，再走主键索引取行数据（回表）。

在 `.idx` 基线之外还有一个 `.idxl` 增量日志：

- 提交时只把本次的 Put/Delete 追加到 `.idxl`，不再重写整份基线（`.idx` 格式不变，仍为版本 2）。
- 加载时先读基线再顺序回放增量；基线缺失/版本不符/增量头部或尾部记录损坏（含截断）时，以行日志为准重建并丢弃增量。
- 增量记录数超过 `max(1000, 基线条目数/2)` 或表关闭时，全量重写基线并清空增量。

### 5.3 维护

INSERT/UPDATE/DELETE 时同步更新关联的二级索引。唯一索引在写入前检查唯一性约束。

### 5.4 键规范化与读取路径

- **字符串键统一大写**入索引，与 SQL `=` 的大小写不敏感语义保持一致；唯一索引因此也是大小写不敏感的（对齐 MySQL 默认排序规则）。`.idx` 文件版本为 2，版本 1 的文件启动时从行数据自动重建。
- **读取**：SQL 层对 `WHERE indexed_col = v` / `IN (v...)` 走 `LookupByIndex` 取主键再回表；命中行超过全表 1/4 且超过 32 行时回退全表扫描。
- **联合索引**：键编码为 `Object[]`，按元素逐位比较（数值跨类型按值、字符串统一大写），因此等值、前缀与下一列范围都能按跳表顺序扫描。SQL 层支持最左前缀 `a = ?`、`a = ? AND b <范围>` 与全列等值；前缀扫描走 `LookupByIndexPrefix`，按 512 条分块顺序取、前缀变化即停。
- **联合索引不落盘**：`.idx` 与 `.idxl` 只编码标量键，联合索引每次启动按行日志重建（单列索引仍走基线 + 增量）。
- **顺序扫描**：`NovaTable.ScanIndexOrder` 沿索引键序（可降序，跳表第 0 层维护前驱指针）逐键回表，供 SQL 层 `ORDER BY` 免排序与 `LIMIT` 提前停止；同一索引键下的主键按升序回表，与「全表扫描后稳定排序」的并列顺序一致。可空列（NULL 不进索引）与字符串/日期列（排序口径与 SQL 不同）不走该路径。
- **限制**：二级索引按写入即时维护，未做 MVCC 版本化（主键索引有）。并发未提交的删除/更新窗口内，索引查询的候选集可能与全表扫描略有差异；返回行仍按可见性与完整 WHERE 复核。

## 6. 设计决策

| # | 决策 | 要点 |
|---|------|------|
| D1 | SkipList 而非 B+ 树 | 实现简单、并发友好，适合内存索引 |
| D2 | 冷热分离 | 千万行仅查热点时内存 < 20MB |
| D3 | .nvi 非跳表镜像 | 持久化稀疏目录，按需重建热点 |
| D4 | 每索引独立文件 | 加载/淘汰/重建互不影响 |
| D5 | 联合索引不落盘 | 键是数组，文件格式只支持标量键，启动按行日志重建 |
| D6 | 行载荷不驻留内存 | 载荷按（偏移，长度）落 `.rlog`，用内存映射窗口按需读（见 §7） |

## 7. 内存占用与内存映射（MMF）

### 7.1 实测构成

200k 行、7 列（含两个二级索引，其中一个联合索引）单表实测托管堆：

| 结构 | 字节/行 | 占比 | 说明 |
|------|--------:|-----:|------|
| 主键索引 + 行版本 | 288 | 43% | 跳表节点 + `List<RowVersion>` + 装箱主键 |
| 联合二级索引 | 312 | 47% | `Object[]` 键 + 每个元素装箱 |
| 单列二级索引 | 70 | 10% | |
| 行载荷 | 120（已移出托管堆） | — | 存在 `.rlog` 中，按映射窗口读取 |

结论：**内存主要被索引与行版本对象占掉，不是文件本身**。同样 200k 行，`.idx` 文件只有 1.6MB。

### 7.2 已完成：载荷走内存映射

行日志是只追加的，每条 Put 记录的载荷在文件中位置固定，因此行版本只保存（偏移，长度）：

- 提交时 `PersistPut` 写入记录后记录偏移，并释放内存中的 `byte[]`。
- 读取走 `RowStore`：整份 `.rlog` 映射一次，内存映射按页按需装入，只有访问过的页占物理内存，内存紧张时由操作系统回收。
- 文件增长后重建映射；`TRUNCATE`/压缩替换文件后必须丢弃旧映射（Windows 对存在映射视图的文件禁止缩短长度）。

效果：托管堆 791 → 671 字节/行；启动加载不再保留「主键字符串 → 载荷」的整表副本。

### 7.3 为什么"直接把 .idx 也 mmap 上来"不解决问题

内存占用不是 `.idx` 文件带来的，而是跳表节点、`List<RowVersion>`、装箱索引键这些托管对象带来的。
只把文件映射进地址空间、结构仍在堆上，内存一分不少。

要让索引真正不占堆，必须让**结构本身**住在映射文件里，即节点按偏移寻址、内存只保留稀疏目录（NewLife.NoDb 的 `DbIndex` 就是这个思路：哈希桶与链表节点全在 `MemoryFile` 中）。

### 7.4 下一步：磁盘有序段索引（两级 LSM）

每个二级索引拆成两层：

| 层 | 位置 | 上限 | 作用 |
|----|------|------|------|
| 不可变有序段 `.idxs` | 磁盘，映射读取 | 全量历史 | 键有序排列，每 64 条一条稀疏目录常驻内存 |
| 内存写层 | 跳表（现有实现） | 条目数或字节阈值 | 承接新写入，读时与段合并结果 |

- **读取**：等值查询在稀疏目录二分定位到块，再在映射窗口内顺序扫该块（约 64 条）；范围/前缀/排序扫段顺序读。
- **写入**：内存写层累积，超过阈值时与旧段归并重写新段（顺序读写，不随机写）。
- **内存**：稀疏目录对 Int32 键约 1.5 字节/行，写层受阈值约束 → 联合索引 312 字节/行降到 10 字节/行以内。

代价（必须接受，否则不做）：

1. 等值查询由「一次内存跳表查找」变成「目录二分 + 一次整块扫描」，微秒级点查会慢一点。
2. 归并带来写放大；阈值定得太小会频繁重写，太大则内存收益变小。
3. 联合索引的键必须能编码成有序字节串（字符串大写、数值按大端、NULL 置前），编码错了会静默错序。

### 7.5 备选方案与取舍

| 方案 | 内存收益 | 实现量 | 主要风险 |
|------|---------|--------|---------|
| A 有序段 + 稀疏目录（推荐） | 索引 312 → <10 B/行 | 中 | 键有序编码、归并写放大 |
| B 索引键压缩（`Object[]` → 有序字节串） | 联合索引约减半 | 小 | 编码/比较语义出错会静默错序 |
| C B+ 树分页索引（MMF 分页 + 页内二分） | 索引接近 0 B/行 | 大 | 页分裂/回收的正确性 |
| D 列式存储 | 扫描最快、压缩比高 | 最大 | 点查与更新语义全变 |

推荐先做 B 再做 A：B 改动小、能立刻把联合索引内存减半，也没有归并写放大的风险；A 是 2000 万行规模的前提。
