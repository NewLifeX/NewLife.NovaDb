# NewLife.NovaDb 索引架构

> 对应模块：N02（主键索引）、N04（二级索引）、N05（冷热分离）
> 关联模块：S03（页读写）、S04（页缓存）

---

## 1. 概述

NovaDb 的索引分两条路线：

- **主键索引（已落盘）**：等值查找走 `.hidx` MMF 哈希字典，范围 / `ORDER BY` / 全表顺序扫描走 `.oidx` 磁盘有序段。结构本身住在映射文件里，打开时不再全表回放，托管堆不保留全表索引。
- **二级索引（已落盘）**：等值 / `IN` / 唯一性检查 / 索引计数走每个索引独立的 `.hidx` MMF 哈希字典；范围、前缀与 `ORDER BY` 首次用到时才从哈希字典重建一份内存跳表（惰性构建，之后随写入增量维护）。基线 `.idx` + 增量 `.idxl` 保留为旧版本兼容与重建依据。

主键索引与二级索引都只保存已提交版本；未提交写入放在表级写集（内存，受事务大小约束）。

## 2. 跳表（SkipList，二级索引的有序层）

### 2.1 结构

概率性多层有序链表，O(log N) 查找/插入/删除：

```
Level 3: HEAD ──────────────────── 50 ───────────── NIL
Level 2: HEAD ── 10 ─────────── 50 ── 70 ────── NIL
Level 1: HEAD ── 5 ─ 10 ── 20 ─ 50 ── 60 ─ 70 ── 90 ── NIL
Level 0: HEAD ── 5 ─ 10 ── 20 ─ 30 ── 50 ── 60 ─ 70 ── 90 ── NIL
```

### 2.2 参数

| 参数 | 值 | 说明 |
|------|---|------|
| MaxLevel | 16 | 支持 2^16 节点高效查找 |
| P | 0.5 | 每节点 50% 概率升层 |

### 2.3 节点内容

节点存储索引键 + 行定位信息（`PageId + Offset`），多层指针用于快速查找与范围扫描。

### 2.4 复杂度

| 操作 | 平均 | 最坏 |
|------|------|------|
| 查找 | O(log N) | O(N) |
| 插入 | O(log N) | O(N) |
| 删除 | O(log N) | O(N) |
| 范围扫描 | O(log N + K) | O(N + K) |

### 2.5 选择 SkipList 的理由

- 实现简单，代码量远小于 B+ 树
- 天然有序，范围扫描友好
- 并发友好（可扩展为 lock-free）
- 作为二级索引的**有序层**按需从 `.hidx` 重建，只服务范围、前缀与 `ORDER BY`；纯等值查询不会触发生成

## 3. 冷热分离

> 现状：主键索引已整体落盘（§4），不再依赖内存热段；本节策略保留给二级索引的后续演进，`HotIndexManager` 当前只用于记录主键访问热度。

### 3.1 架构

```
┌──────────────────────────────────┐
│ 热索引 (HotIndexManager)         │  ← 最近访问的数据段
│ 完整 SkipList 节点                │     O(log N) 查找
├──────────────────────────────────┤
│ 冷索引 (ColdIndexDirectory)       │  ← 长期未访问
│ 稀疏目录（每 N 行一个锚点）        │     查询时按需加载
└──────────────────────────────────┘
```

### 3.2 热索引管理器（HotIndexManager）

管理热段，将最近访问的数据段完整加载到内存跳表：

- **热数据窗口**：默认 600 秒（`HotWindowSeconds`），窗口内保持热索引
- **冷淘汰阈值**：默认 1800 秒（`ColdEvictionSeconds`），超过则卸载
- **热段最大行数**：默认 100 万行
- **LRU 淘汰**：按最后访问时间排序，超时自动降级

段元数据（`IndexSegment`）：段 ID、是否热段、键范围（MinKey/MaxKey）、行数、最后访问时间。

### 3.3 冷索引目录（ColdIndexDirectory）

长期未访问的数据段仅保留稀疏目录：

```
锚点 0: Key=1    → PageId=0,  Offset=0
锚点 1: Key=1001 → PageId=5,  Offset=128
锚点 2: Key=2001 → PageId=10, Offset=256
...
```

- **锚点间隔**：默认每 1000 行
- **查找流程**：二分搜索稀疏目录 → 定位锚点 → 从锚点页顺序扫描
- **访问提升**：频繁访问的冷段自动提升为热段

### 3.4 冷热访问流程

```
查询 key=5000:
  1. 热索引查找 → 未命中
  2. 冷索引二分搜索 → 锚点(key=4000, offset=1234)
  3. MMF 加载锚点后 1000 行
  4. 构建热索引段(key=4000~5000)
  5. 缓存到热索引管理器
  6. 返回 key=5000 数据
```

### 3.5 内存效果

| 场景 | 全量索引 | 冷热分离 | 节省 |
|------|---------|---------|------|
| 1000 万行，查最近 10 万行 | ~1.5GB | ~15MB | 99% |
| 1 亿行，查最近 100 万行 | ~15GB | ~150MB | 99% |

## 4. 主键索引文件（.hidx / .oidx）

### 4.1 多索引多文件

- 主键哈希索引：`{Table}.hidx`
- 主键有序索引：`{Table}.oidx`
- 二级索引（未迁移）：`{Table}_{IndexName}.idx` + `.idxl`

### 4.2 哈希字典（.hidx）

```
[FileHeader 32B][MetaSlot0 160B][MetaSlot1 160B][桶数组 Int64 × capacity][节点区（追加写）]
键节点：[NextKey][Hash][KeyLength][ValueCount][ValueHead][ValueTail][key]
值节点：[NextValue][Length][Flags][payload]
```

- 键编解码：每列一段 `[长度][按列类型编码的内容]`，SQL 传入的 Int32/Int64 归一到同一字节串。
- 哈希：FNV-1a 64 + murmur3 收尾，不用 `GetHashCode`（逐进程随机化会导致重启后索引失效）。
- 查找：`hash & (capacity-1)` → 桶槽 8B → 链内比较键字节 → 值链；全程只读映射视图，不构造节点对象。
- 写入：按批预留节点空间并把 `ArenaEnd` 落盘，节点写在预留区内（预留多于实际时差额记死区）；崩溃后旧结构仍完整，回放按 `unique` 语义幂等。
- 扩容：载重超过 0.75 时追加 2 倍桶数组并**原地重链**——只改每个键节点的 `NextKey` 指针，不复制节点、不读键内容；
  重链按**分块迁移**推进：每次写入最多迁移 32768 个键节点，迁移期间新旧两张桶表同时有效（旧桶 `[0, 游标)` 已迁空，其余键仍在旧表），
  查询按「键的旧桶下标是否小于游标」决定查哪张表，中途崩溃后下次写入继续迁移。
- 元数据双槽交替写入并带 CRC，单槽损坏不会触发整表重建。
- 文件版本 2（`FileVersion=2`）在元数据中新增**存活值计数** `LiveCount`：挂链 +1，`MarkValueDeleted` 打删除标记 -1（值节点 `Flags` bit0）。无并发写事务时 `COUNT(*)` 直接取该计数，O(1) 返回；旧版本索引文件启动时按行日志重建一次。

主键版本记录固定 32B：`[CreatedTx][DeletedTx][DataOffset][DataLength]`。更新时新版本追加，旧版本的 `DeletedTx` 由 `MarkValueDeleted` 原地补丁并递减存活计数。

### 4.3 有序段（.oidx）

```
[FileHeader][MetaSlot0][MetaSlot1][RunIndex 32B × 1024][Run0][Run1]...
Run = [RunHeader 40B][条目区（按键升序）][偏移目录 Int64 × EntryCount]
条目 = [SortPrefix][CreatedTx][DeletedTx][DataOffset][DataLength][Flags][KeyLength][key]
```

- 提交时条目先进内存写缓冲，缓冲满（默认 65536 条）或关闭时整体写出一个新 run；条目按「先填托管缓冲、再整块写一次」写出，单条目只有一次映射调用。
- 读取时对全部 run + 写缓冲做 k 路归并；同一键若有多个版本，用删除标记挑出最新存活版本。降序扫描按方向取最大键，多 run 同样正确。
- 归并扫描越过上界（升序的 `to` / 降序的 `from`）立即结束，范围扫描代价为 O(log N + K)，与表规模无关。
- run 数超过 12 时按**体量分层合并**：只挑同一量级里最小的 4 个 run 归并成新 run，单次重写量与层内规模成正比而不是全表规模。触发合并时**不刷写缓冲**，让 run 规模保持均匀。
  - 合并**分块推进**：每次触发只归并 16384 条（`MergeChunkEntries`），剩余部分在后续提交里继续，把原来可达秒级的单次停顿摊成几十毫秒。
  - 输出区块在开始时就按来源精确预算（条目区与偏移目录大小都等于各来源之和）并整体预留给 `ArenaEnd`，因此合并期间的新 run 不会覆盖半成品；中途崩溃或截断时这段输出只是垃圾空间，来源 run 仍在索引里。
  - 新 run 先登记进 run 索引并落元数据，再把旧 run 的槽位清零标记失效——任何崩溃点都能从元数据引用的 run 里读回全部条目，最坏只是重复合并。
  - 失效槽位进入空闲列表，后续 run 复用它们，run 索引槽位不会因反复合并而耗尽。
  - 垃圾空间超过 `max(8MB, 存活字节) × 3` 时才做一次全量重写，回收空间并丢弃旧版本与已删除条目。
- 数值 / 时间 / 布尔主键带 8 字节可比较前缀，二分定位时无需反复解码。

### 4.4 启动与恢复

- 索引是行日志的派生数据：提交时只推进**内存中的**已应用偏移，持久化偏移按 `DbOptions.IndexFlushIntervalMs`（默认 1000ms，0 表示每次提交）成批前进，关闭时强制刷盘。
- 周期性刷盘只保证元数据与写缓冲落盘（`MmfRegion.Flush(syncView: false)`）；强制回写整个映射视图留到关闭、压缩等显式节点。索引文件可达数百 MB，每秒一次 `FlushViewOfFile` 会让写入抖动上百毫秒。
- 正常关闭：两个文件都记录 `AppliedOffset == rlog 长度`，打开直接可用。
- 崩溃或索引缺失：任一侧持久化偏移落后即按 `.rlog` 整表重建（先回放得到每个主键的存活版本，再批量写索引）。
- 只读模式：索引必须已是最新，否则提示先以读写模式打开一次完成重建。

## 5. 二级索引（P1）

### 5.1 类型

| 类型 | 说明 |
|------|------|
| 普通索引 | 加速 WHERE 条件查询 |
| 唯一索引 | 加速查询 + 唯一性约束 |
| 联合索引 | 多列组合，最左前缀匹配 |

### 5.2 存储

每个二级索引一个 `.hidx`（MMF 哈希字典），条目为 `(索引键字节, 主键字节)`；查询先定位主键，再回表取行。

| 文件 | 角色 |
|------|------|
| `{表}_{索引}.hidx` | 权威哈希字典。写入即时生效，`AppliedOffset` 与行日志长度一致时启动直接使用，不读其他文件 |
| `{表}_{索引}.idx` | 全量基线（旧格式，版本 2）。`.hidx` 缺失、损坏或偏移落后时作为重建来源之一 |
| `{表}_{索引}.idxl` | 增量日志，提交时追加 Put/Delete。**启动时不回放**：回放需要逐条沿值链去重，低基数列上退化成 O(N²)（百万行实测 7 分钟），存在增量即从主键索引全表重建（O(N)，秒级） |

启动顺序：`.hidx` 偏移对齐 → 直接使用；否则若 `.idx` 基线可用且**增量已清空** → 直接加载基线填充 `.hidx`；其余情况（增量非空、基线缺失/版本不符、联合索引无基线）→ 从主键索引全表重建。崩溃恢复实测：91 万行表 4.7 秒（此前按增量逐条去重回放要 7 分钟以上）。

`.idx` 基线仍在两种时机全量重写：增量记录数超过 `max(1000, 基线条目数/2)`、表正常关闭时；此时顺带清空 `.idxl`、推进 `.hidx` 的 `AppliedOffset`，死条目占比过半时压缩 `.hidx` 回收追加区。

**运行期文件缺失**（运维删除或移走）：

| 文件 | 引擎行为 |
|------|---------|
| `.hidx` | 注销该索引：查询不再选它、回退全表扫描，写入不再维护它；同时删除 `.idx` 基线与 `.idxl` 增量（它们相对当前行日志已不可信），重启后从主键索引重建 |
| `.idx` / `.idxl` | 运行期不读取，删除无影响 |

降级期间唯一索引不再做唯一性检查，只记录告警；`_sys.table_files` 把该索引标记为 `degraded`。

### 5.3 维护

INSERT/UPDATE/DELETE 时同步更新关联的二级索引哈希字典（若内存有序层已构建，同步维护）。唯一索引在写入前用哈希字典做唯一性检查（非唯一索引跳过该检查，避免每行扫描值链）。

写入路径为批量导入做过这些取舍：

- **增量按事务聚合**：一次提交只把本事务的 Put/Delete 合成一批追加到 `.idxl`、只推进一次内存中的 `.hidx` 偏移；哈希字典的持久化偏移按 `IndexFlushIntervalMs` 成批前进，崩溃后偏移落后于行日志，启动时按增量回放或整表重建。
- **不做无谓去重**：正常写入不扫描值链（唯一索引的链长恒为 1），只有「基线 + 增量回放」需要幂等，才让哈希字典跳过重复值。
- **列序号缓存**：索引列在表中的位置按索引缓存，表结构变更时清空。
- **更新时索引键未变则跳过维护**：`UPDATE` 原本无条件「先移除旧值再插入新值」，低基数列的值链可达数千个主键，改一列不相关的字段也要在链上走一趟。现在先比较新旧行的索引键，键相同就两侧都跳过：100 万行表 `UPDATE` 244µs → 16µs。
- **压缩阈值按下标条目数增长**：阈值取 `max(10000, 基线条目数 / 2)`，基线条目数用**存活值数**（索引条目总数）而不是不同键数。低基数列（状态、类型）的不同键可能只有几十个，按不同键数会让阈值恒定在 10000，每万次写入就全量重写一次索引，百万行规模直接退化为 O(N²)：实测 100 万行表单条插入 88µs → 19µs，批量装载同比例加速。
- **偏移对齐即丢弃增量**：`.hidx` 的 `AppliedOffset` 等于行日志长度时，`.idxl` 里的条目必然已进哈希，启动时直接把增量文件删掉，防止残留文件越攒越多。

### 5.4 键规范化与读取路径

- **字符串键统一大写**入索引，与 SQL `=` 的大小写不敏感语义保持一致；唯一索引因此也是大小写不敏感的（对齐 MySQL 默认排序规则）。`.idx` 文件版本为 2，版本 1 的文件启动时从行数据自动重建。
- **读取**：SQL 层对 `WHERE indexed_col = v` / `IN (v...)` 走 `LookupByIndex` 取主键再回表；命中行超过全表 1/4 且超过 32 行时回退全表扫描。等值、`COUNT` 快路径只读 `.hidx`，不构建内存结构。
- **联合索引**：键编码为一串按列编码的字节（数值/时间/布尔带可比较前缀，字符串统一大写），逐列比较等价于逐元素比较。等值、前缀与下一列范围都支持；前缀扫描走 `LookupByIndexPrefix`，需要有序层时按需生成，按 512 条分块顺序取、前缀变化即停。
- **联合索引同样落盘**：`.hidx` 支持多列键，因此联合索引重开后不再需要按行日志重建；旧 `.idx` 只支持标量键，联合索引没有基线，`.hidx` 丢失时从主键索引重建。
- **顺序扫描**：`NovaTable.ScanIndexOrder` 沿索引键序（可降序，跳表第 0 层维护前驱指针）逐键回表，供 SQL 层 `ORDER BY` 免排序与 `LIMIT` 提前停止；同一索引键下的主键按升序回表，与「全表扫描后稳定排序」的并列顺序一致。可空列默认不走该路径（NULL 不进索引）；当索引条目数等于存活行数（即列中无 NULL）时放行，否则退回全表扫描 + 排序以保留 NULL 行。字符串/日期列排序口径与 SQL 不同，始终不走该路径。
- **列类型变更**：`ALTER TABLE ... MODIFY COLUMN` 改了索引列或主键类型时，旧键编码失效，按新类型重建对应 `.hidx`（只重建类型变化的索引）。
- **只读模式**：`.hidx` 偏移不对齐且无法重建时不注册该索引，查询自动退回全表扫描，不改写任何文件。
- **限制**：二级索引按写入即时维护，未做 MVCC 版本化（主键索引有）。并发未提交的删除/更新窗口内，索引查询的候选集可能与全表扫描略有差异；返回行仍按可见性与全表复核。

## 6. 设计决策

| # | 决策 | 要点 |
|---|------|------|
| D1 | 主键索引落盘（哈希 + 有序段） | 结构住在映射文件里，等值 O(1)，范围走有序段；打开不再全表回放 |
| D2 | 二级索引同样落 `.hidx` | 等值、唯一性检查、计数读哈希字典；有序层按需从哈希字典重建，纯等值查询不占内存 |
| D3 | 哈希与有序分离 | 哈希只服务等值，有序段只服务范围/排序；各自独立重建，失败隔离 |
| D4 | 每索引独立文件 | 加载/淘汰/重建互不影响 |
| D5 | 联合索引只落 `.hidx` | 旧 `.idx` 基线格式只支持标量键；`.hidx` 支持多列键，丢失时从主键索引重建 |
| D6 | 行载荷不驻留内存 | 载荷按（偏移，长度）落 `.rlog`，用内存映射窗口按需读（见 §7） |
| D7 | 索引只存已提交版本 | 未提交写入放表级写集；索引的 `AppliedOffset` 永远不超前于行日志 |
| D8 | 崩溃后整表重建 | 任一侧偏移落后即重建，不做部分修复；正常关闭时两文件偏移一致 |
| D9 | 索引文件可在线移除 | 主键索引缺失立即按行日志重建；二级索引缺失注销并回退全表扫描；见[存储架构.md](存储架构.md) §10 |

## 7. 内存占用与内存映射（MMF）

### 7.1 实测构成（迁移前基线）

200k 行、7 列（含两个二级索引，其中一个联合索引）单表实测托管堆：

| 结构 | 字节/行 | 占比 | 说明 |
|------|--------:|-----:|------|
| 主键索引 + 行版本 | 288 | 43% | 跳表节点 + `List<RowVersion>` + 装箱主键 |
| 联合二级索引 | 312 | 47% | `Object[]` 键 + 每个元素装箱 |
| 单列二级索引 | 70 | 10% | |
| 行载荷 | 120（已移出托管堆） | — | 存在 `.rlog` 中，按映射窗口读取 |

结论：**内存主要被索引与行版本对象占掉，不是文件本身**。

### 7.2 已完成：载荷走内存映射

行日志是只追加的，每条 Put 记录的载荷在文件中位置固定，因此行版本只保存（偏移，长度）：

- 提交时写入记录后记录偏移，并释放内存中的 `byte[]`。
- 读取走 `RowStore`：整份 `.rlog` 映射一次，内存映射按页按需装入，只有访问过的页占物理内存，内存紧张时由操作系统回收。
- 文件增长后重建映射；`TRUNCATE`/压缩替换文件后必须丢弃旧映射（Windows 对存在映射视图的文件禁止缩短长度）。

### 7.3 已完成：主键索引整体落盘

主键索引改为 `.hidx`（哈希字典）+ `.oidx`（磁盘有序段）后：

- 托管堆不再保留全表跳表与 `List<RowVersion>`，只剩活跃事务写集（受事务大小约束）。
- 正常关闭后打开成本为 O(1)：只校验文件头与元数据，不回放行日志。
- 崩溃或索引缺失时按行日志重建；重建只保留每个主键的存活版本，不保留历史版本。
- 点查由「一次内存跳表查找」变成「桶定位 + 少量映射读」，页命中时接近内存，冷数据由操作系统换页。

### 7.4 已完成：二级索引迁移（等值落盘 + 有序层惰性）

二级索引现在由三层组成：

| 层 | 位置 | 作用 |
|----|------|------|
| `{表}_{索引}.hidx` | 磁盘，映射读取 | 等值、`IN`、唯一性检查、索引计数 |
| 内存跳表 | 托管堆，**首次范围/前缀/`ORDER BY` 时才生成** | 范围、前缀、`ORDER BY`、`ANALYZE` 采样 |
| `.idx` + `.idxl` | 磁盘，全量读 | 旧基线兼容与重建来源 |

- 纯等值负载（最常见）不再有任何索引常驻内存结构；联合索引 312 字节/行降到映射文件里，托管堆只剩桶数组所在的映射页。
- 一旦执行范围或排序查询，会一次性构建该索引的内存跳表，之后随写入增量维护；服务重启后再次惰性构建。
- 列类型变更（`ALTER TABLE ... MODIFY`）后旧键字节失效，只重建类型变化的那些索引。
- `.hidx` 死条目占比过半时在重写基线后压缩，避免追加区无限增长。

2 万行、单列二级索引（`score INT NOT NULL`，每值约 200 行）实测（`Benchmark/MmfSecondaryIndexBenchmark`，.NET 8，含 SQL 解析）：

| 操作 | 平均耗时 |
|------|--------:|
| 二级等值查询（`WHERE score = ?`，回表约 200 行） | 258 µs |
| 二级等值计数（index-only，不回表） | 41 µs |
| 按索引顺序取前 100 行（`ORDER BY score LIMIT 100`） | 45 µs |
| 按索引顺序分页（单列 + `OFFSET`） | 50 µs |
| 带二级索引插入单行（每行一个事务） | 352 µs |

写入吞吐（2 万行，一次性插入，含 SQL 解析；单位行/s）：

| 场景 | 优化前 | 现在 |
|------|-------:|-----:|
| 无索引 / 多行语句（每批 1000 行） | 159k | 156k |
| 1 个二级索引 / 多行语句（每批 1000 行） | 11.6k | 84k |
| 2 个二级索引 / 多行语句（每批 1000 行） | 6.8k | 74k |
| 1 个二级索引 / 逐条插入（每行一个事务） | 3.1k | 3.3k |

优化前后差异集中在「每个事务只刷一次索引」：逐行提交的 OLTP 场景受行日志与索引的每次提交刷盘限制，量级不变。

### 7.5 取舍

| 方案 | 内存收益 | 实现量 | 主要风险 |
|------|---------|--------|---------|
| A 哈希 + 有序段（主键）／哈希 + 惰性跳表（二级） | 等值负载索引接近 0 B/行 | 中 | 键编码、归并可见性、崩溃重建 |
| B 仅索引键压缩 | 联合索引约减半 | 小 | 编码/比较语义出错会静默错序 |
| C B+ 树分页索引 | 索引接近 0 B/行，单结构同时支持等值与范围 | 大 | 页分裂/回收的正确性 |
| D 列式存储 | 扫描最快、压缩比高 | 最大 | 点查与更新语义全变 |

当前选择 A：哈希与有序段职责单一、可独立重建；代价是每行约 150B 的索引写放大与一次额外的映射读。

### 7.6 存储层性能专项（2026-11）

固定时长微基准（Release，Windows，2 万行单表，含 SQL 解析），优化前后对比：

| 场景 | 优化前 | 优化后 | 变化 |
|------|-------:|-------:|-----:|
| `SELECT COUNT(*)` | 21.9 ms | 2.3 µs | 约 9500× |
| 带二级索引单行插入 | 367 µs | 22 µs | 约 17× |
| 单行更新 | 474 µs | 15 µs | 约 32× |
| 删除 + 重插 | 826 µs | 71 µs | 约 12× |
| 范围查询 1000 行 | 4.23 ms | 0.29 ms | 约 15× |
| 范围查询 10 行 | 3.45 ms | 22 µs | 约 160× |
| 可空列 `ORDER BY ... LIMIT 100`（无 NULL） | 41 ms | 40 µs | 约 1000× |
| 二级索引等值计数 | 21 µs | 3.3 µs | 约 6× |
| 主键点查 | 5.1 µs | 3.7 µs | 约 1.4× |
| 批量装载（1000 行/语句） | 4.8 万行/s | 19~31 万行/s | 约 4~6× |
| 3000 批连续写入 p99 / max（20 万行起） | — / 7284 ms | 22 ms / 250 ms | 最大值降 97% |
| 100 万行表的单条插入 / 更新 | — | 17 µs / 16 µs | 与表规模基本无关 |
| 崩溃后恢复（91 万行，杀进程再开） | — | 4.7 s | 由增量逐条去重回放（>7 分钟）改为整表重建 |
| Full 模式 10 万行批量导入 | 186.9 s | 0.89 s | 刷盘按提交聚合，快 210× |
| 4KB 大字段行：插入 / 点查 | — | 69 MB/s / 25 µs | — |
| 51 列宽表：插入 / 点查（2 列） | — | 2.5 万行/s / 18 µs | — |

主要原因与对应机制：

1. **范围扫描不提前结束**：有序段归并越过上界后没有退出，每次范围查询都会扫到尾部；现已按扫描方向在越界条目处立即返回。
2. **`COUNT(*)` 反序列化整表**：无并发写事务时改为读取哈希字典维护的存活值计数，O(1)。
3. **每次提交强制刷索引视图**：`FlushViewOfFile` 在数百 MB 的映射视图上要几十到几百毫秒；改为「内存推进偏移 + 间隔刷盘 + 崩溃重建」，周期刷盘只落元数据，强制回写留给关闭与压缩。仅此一项把连续批量写入吞吐从 6.5 万行/s 提到 12 万行/s 以上。
4. **有序段全量重写造成秒级停顿**：run 数超限后原本重写整个文件，200 万行规模单次停顿 1.8~7.3 秒；改为分层合并——只重写同量级最小的 4 个 run、槽位复用、垃圾过半才全量回收。触发合并时不再顺带刷写缓冲，run 规模保持均匀；一次合并再拆成每批 16384 条分块推进，跨多次提交完成，单次停顿降到几十毫秒。批量写入 p99 从 30ms 级降到 19ms，最大值从 7.3 秒降到 0.8 秒。
5. **哈希索引扩容复制全部键节点**：载重 0.75 触发 2 倍扩容时逐键复制节点并分配键数组，300 万键要 0.9~1.5 秒；改为原地重链，只改 `NextKey` 指针。
6. **哈希索引批量预留区被当成死区**：预留在前、节点写在后，每批都留下一整份同规模废区，`.hidx` 因此翻倍；修正为节点写在预留区内，文件减半、随之降低扩容与刷盘成本。
7. **点查与全表扫描的包装分配**：无未提交写集时跳过 `ComparableObject` 与跳表查找、热点管理器无热段时零开销、全表/范围扫描跳过主键解码与中间版本列表。
8. **规划阶段重复扫描值链**：二级索引等值查询在统计缺失时用哈希字典的值链长度做 O(1) 估算，主键列表留到执行阶段再取；二级等值计数 21µs → 4.3µs。
9. **多 run 降序扫描返回空**：归并取候选时只用键大小比较、未考虑扫描方向，run 多于一个时降序范围扫描结果为空；已按方向取最大键。
10. **逐字段访问映射视图**：每个有序段条目原来要十几次 `Read/Write` 映射视图调用，哈希节点每次 7~8 次；改为「先填到托管缓冲、再整块写一次；固定头一次读入再解析」，范围扫描、合并、压缩与批量插入一起受益。
11. **二级索引压缩阈值按不同键数计算**：低基数列的不同键只有几十个，阈值恒为下限 10000，百万行表每万次写入就全量重写整份索引基线（O(N²)）。改为按存活值数计算后，100 万行表单条插入 88µs → 19µs，批量装载里的重复压缩一并消失。
12. **更新无条件重建二级索引条目**：`UPDATE` 不论索引列是否变化都「先移除旧值再插入新值」，低基数列的值链可达数千个主键，改一列无关字段也要在链上走一趟。改为比较新旧行的索引键、相同即跳过，2 万行表 `UPDATE` 68µs → 16µs，100 万行表 244µs → 16µs。
13. **崩溃恢复按增量逐条去重回放**：`.idxl` 回放要给每条记录沿值链找重复，低基数列单链上万主键，91 万行实测 446 秒；改为「增量非空即整表重建」后 4.7 秒完成，且计数、全表扫描、二级索引计数、点查与排序结果一致。
14. **提交时只刷一次盘**：一次千行 `INSERT` 如果在每条记录上 fsync，Full 模式 10 万行导入要 187 秒；改为「事务提交刷一次」后 0.89 秒。随后进一步取消从未参与重放的表级 WAL，Full 模式只剩行日志一次 `Flush(true)`，单行提交 2.2ms → 1.09ms。
15. **哈希扩容整表重链**：载重超 0.75 时一次把全部键节点迁移到新桶表，300 万键要 0.9 秒且期间无法提交；改为分块迁移（每次写入迁 32768 个节点），迁移期间双桶表并存、按游标选表。连续批量写入的最大停顿从 870ms 降到 250ms 以内。

> 说明：本节为固定时长循环基准（非 BenchmarkDotNet），绝对值跨机器不可比，仅用于同一环境下的前后对比。
