## 1. 系统架构概览

NewLife.NovaDb（诺娃数据库）是一个纯 C# 实现的混合数据库引擎，支持 .NET Framework 4.5+（含 .NET Core / .NET 5~10），支持嵌入式/网络双模部署。融合关系型、时序、消息队列、KV 能力。

### 1.1 核心特性

- **纯 C# 实现**：无 native 依赖，跨平台一致
- **双模部署**：嵌入模式（进程内）/ 网络模式（独立进程）
- **混合引擎**：Nova（关系型）+ Flux（时序 + MQ）+ KV（键值）
- **MVCC 事务**：Read Committed 隔离级别，乐观并发
- **索引落盘**：主键走 MMF 哈希字典（等值）+ 磁盘有序段（范围/排序），二级索引每个独立 `.hidx` 哈希字典、有序层按需构建；打开不再全表回放
- **双日志**：WAL（崩溃恢复）+ Binlog（主从复制）

## 2. 统一入口与四大场景

### 2.1 核心概念

**连接字符串 = 数据库**。一个连接字符串对应一个数据库，数据库内可同时包含：
- **多张关系表**（Nova 引擎）
- **多张时序表**（Flux 引擎，同时作为 MQ 的底层存储）
- **多个 KV 库**（KvStore 引擎，按表名隔离）

四大场景共用同一个连接字符串，共用同一数据库目录（嵌入模式）或同一服务端连接（网络模式）。

### 2.2 统一入口 `NovaClientFactory`

`NovaClientFactory` 继承 `DbProviderFactory`，是所有场景的统一入口：

```
NovaClientFactory (统一入口，单例 Instance)
│
├── CreateConnection()           → NovaConnection (ADO.NET)
│   用于：关系型 SQL、时序 SQL、DDL
│
├── GetCacheProvider(connStr)    → NovaCacheProvider (ICacheProvider)
│   用于：同时需要 KV 缓存 + MQ 队列的场景
│   └── .Cache                  → ICache (默认 KV 表)
│   └── .GetCache(tableName)    → ICache (指定 KV 表)
│   └── .GetQueue<T>(topic)     → IProducerConsumer<T> (MQ 队列)
│
├── GetCache(connStr, tableName) → ICache (NovaCache)
│   用于：仅需 KV 缓存，直接获取指定表
│
└── GetQueue<T>(connStr, topic)  → IProducerConsumer<T> (NovaQueue)
    用于：仅需 MQ 队列，直接获取指定 topic
```

### 2.3 双模式架构

#### 2.3.1 嵌入模式

连接字符串：`Data Source=../data/mydb`

```
NovaClientFactory
  └── EmbeddedDatabase (按数据库目录缓存，同一目录共用实例)
        ├── SqlEngine           → 关系型/时序 SQL 操作
        ├── KvStore × N         → 多个 KV 表 (kv_default, kv_session, ...)
        └── FluxEngine          → 时序表 + MQ 队列 (共用引擎)
```

- 同一数据库目录只创建一个 `EmbeddedDatabase` 实例，避免引擎重复创建
- `NovaConnection.Open()` 时通过 `EmbeddedDatabase` 获取 `SqlEngine`
- `GetCache()` 通过 `EmbeddedDatabase.GetKvStore(tableName)` 获取 KV 引擎
- `GetQueue()` 通过 `EmbeddedDatabase.FluxEngine` 获取 Flux 引擎
- 数据库目录结构：

```
mydb/                                  ← 数据库目录 (连接字符串指向此处)
├── nova.db                            ← 库级文件头
├── users.schema                       ← 表结构
├── users.rlog                         ← 行数据（Append-Only）
├── users.hidx / users.oidx            ← 主键哈希/有序索引
├── users_email.hidx / .idx / .idxl    ← 二级索引（每个索引独立）
├── users.wal
├── flux.rlog / flux.col               ← Flux 引擎 (时序 + MQ)
├── kv_default/                        ← KV 表 "default"
├── kv_session/                        ← KV 表 "session"
└── nova.000001.binlog                 ← Binlog（网络模式）
```

> 实际文件扩展名：行数据 `.rlog`、表结构 `.schema`、主键索引 `.hidx`/`.oidx`、二级索引 `{表}_{索引}.hidx`/`.idx`/`.idxl`、WAL `.wal`（TableFileManager 约定）。`.data` 已停止创建，仅为旧库兼容保留。

#### 2.3.2 网络模式

连接字符串：`Server=localhost;Port=3306;Database=mydb`

```
NovaClientFactory
  └── NovaPoolManager
        └── NovaClientPool (按连接字符串缓存，共用连接池)
              └── NovaClient × N (RPC 客户端，从池中借用/归还)
                    ├── Nova/* → SQL 操作 (Execute/Query/Transaction)
                    ├── Kv/*   → KV 操作 (Set/Get/Delete/Exists)
                    └── Flux/* → MQ 操作 (Publish/ReadGroup/Ack)
```

- 同一连接字符串共用一个 `NovaClientPool`，复用 TCP 连接
- `NovaConnection.Open()` 从连接池借用 `NovaClient`，`Close()` 时归还
- `GetCache()` 从连接池借用 `NovaClient`，封装为 `NovaCache`
- `GetQueue()` 从连接池借用 `NovaClient`，封装为 `NovaQueue`
- 四大场景共用同一个连接池，无需为不同场景建立独立连接

### 2.4 四大场景使用方式

#### 场景 1：关系型（Nova 引擎）— ADO.NET SQL

```csharp
// 通过 ADO.NET 标准接口操作关系表，嵌入/网络模式仅连接字符串不同
var factory = NovaClientFactory.Instance;
using var conn = (NovaConnection)factory.CreateConnection();
conn.ConnectionString = "Data Source=../data/mydb";  // 嵌入模式
// conn.ConnectionString = "Server=host;Port=3306;Database=mydb";  // 网络模式
conn.Open();

// DDL
conn.ExecuteNonQuery("CREATE TABLE users (id INT PRIMARY KEY, name STRING(50), age INT)");

// DML
using var cmd = conn.CreateCommand();
cmd.CommandText = "INSERT INTO users (id, name, age) VALUES (@id, @name, @age)";
cmd.Parameters.Add(new NovaParameter("@id", 1));
cmd.Parameters.Add(new NovaParameter("@name", "Alice"));
cmd.Parameters.Add(new NovaParameter("@age", 25));
cmd.ExecuteNonQuery();

// 查询
cmd.CommandText = "SELECT * FROM users WHERE age > @minAge";
cmd.Parameters.Clear();
cmd.Parameters.Add(new NovaParameter("@minAge", 18));
using var reader = cmd.ExecuteReader();
```

#### 场景 2：时序库（Flux 引擎）— ADO.NET SQL

```csharp
// 时序表通过 ENGINE=FLUX 创建，同样使用 ADO.NET SQL 操作
using var conn = new NovaConnection("Data Source=../data/mydb");
conn.Open();

// 创建时序表
conn.ExecuteNonQuery(@"CREATE TABLE metrics (
    time DATETIME, device STRING(32), temperature DOUBLE, humidity DOUBLE
) ENGINE=FLUX");

// 写入时序数据
conn.ExecuteNonQuery(@"INSERT INTO metrics (time, device, temperature, humidity)
    VALUES (NOW(), 'sensor-01', 23.5, 65.2)");

// 时间范围聚合查询
using var cmd = conn.CreateCommand();
cmd.CommandText = @"SELECT device, AVG(temperature), MAX(humidity)
    FROM metrics WHERE time > @start GROUP BY device";
cmd.Parameters.Add(new NovaParameter("@start", DateTime.Now.AddHours(-1)));
using var reader = cmd.ExecuteReader();
```

#### 场景 3：KV 缓存 — ICache API

```csharp
var factory = NovaClientFactory.Instance;
var connStr = "Data Source=../data/mydb";  // 或网络模式连接字符串

// 方式 1：直接获取指定 KV 表
ICache cache = factory.GetCache(connStr, "session");
cache.Set("user:1001", new UserInfo { Name = "Alice" }, 3600);
var user = cache.Get<UserInfo>("user:1001");

// 方式 2：通过 CacheProvider 获取多个 KV 表
var provider = factory.GetCacheProvider(connStr);
ICache defaultCache = provider.Cache;                  // 默认 KV 表
ICache sessionCache = provider.GetCache("session");    // session 表
ICache configCache = provider.GetCache("config");      // config 表
```

#### 场景 4：MQ 消息队列 — IProducerConsumer API

```csharp
var factory = NovaClientFactory.Instance;
var connStr = "Data Source=../data/mydb";

// 方式 1：直接获取指定 topic 的队列
var queue = factory.GetQueue<OrderEvent>(connStr, "orders", "order-processor");
queue.Add(new OrderEvent { OrderId = 1001, Action = "created" });

// 方式 2：通过 CacheProvider 获取队列
var provider = factory.GetCacheProvider(connStr);
var eventQueue = provider.GetQueue<OrderEvent>("orders", "order-processor");
```

#### 综合场景：四合一

```csharp
// 同一连接字符串覆盖四大场景
var connStr = "Data Source=../data/mydb";
var factory = NovaClientFactory.Instance;

// ① 关系型 — ADO.NET
using var conn = new NovaConnection(connStr);
conn.Open();
conn.ExecuteNonQuery("INSERT INTO users (id, name) VALUES (1, 'Alice')");

// ② 时序库 — ADO.NET
conn.ExecuteNonQuery("INSERT INTO metrics (time, device, value) VALUES (NOW(), 's1', 23.5)");

// ③ KV 缓存 — ICache
var cache = factory.GetCache(connStr, "session");
cache.Set("token:abc", "user-1001", 3600);

// ④ MQ 队列 — IProducerConsumer
var queue = factory.GetQueue<String>(connStr, "notifications", "push-service");
queue.Add("New order #1001");
```

### 2.6 关键设计决策

| 决策 | 说明 |
|------|------|
| **连接字符串即数据库** | 一个连接字符串对应一个数据库目录/远程库，内含所有引擎数据 |
| **嵌入模式引擎共用** | 同一目录的 EmbeddedDatabase 全局缓存，避免多次创建引擎 |
| **网络模式连接池共用** | 四大场景共用 NovaClientPool，NovaClient 支持 SQL/KV/MQ 全部 RPC |
| **关系型/时序走 ADO.NET** | SQL 操作通过 NovaConnection → SqlEngine/NovaClient，标准接口 |
| **KV 走 ICache** | NovaCache 封装 KvStore（嵌入）或 NovaClient.Kv*（服务器） |
| **MQ 走 IProducerConsumer** | NovaQueue 封装 FluxEngine（嵌入）或 NovaClient.Flux*（服务器） |
| **NovaCacheProvider 聚合** | 同时提供 ICache + IProducerConsumer，适合同时需要缓存和队列的场景 |

## 4. 设计决策记录（DDR）

### D1: 纯托管实现
不引入 native 依赖，保持跨平台一致性。

### D2: MMF 作为主要存储
利用操作系统虚拟内存管理，64 位系统 128TB 虚拟地址空间，OS 按需分页映射。

### D3: 索引整体落盘（主键哈希+有序段、二级哈希+惰性有序层）

主键索引拆成 MMF 哈希字典（等值）与磁盘有序段（范围/排序），结构住在映射文件里，托管堆不保留全表索引。
二级索引同样每个索引一个 `.hidx` 哈希字典，等值/唯一性检查/计数只读映射文件；范围、前缀与 `ORDER BY` 首次用到时才从哈希字典构建内存跳表（惰性），之后随写入增量维护。

### D4: Read Committed 隔离级别
平衡一致性与并发性能，满足大多数业务场景。

### D5: 表级 WAL
每表独立 WAL，减少并发竞争，简化恢复。

### D6: 冷热分离索引
千万行表仅查热点时内存 < 20MB，冷数据自动卸载至 MMF。

### D7: SQL 子集策略
覆盖 ~60% SQL92 标准，聚焦业务常用场景，不追求完整性。

### D8: Nova 不分片
单表单文件，MMF 高效处理超大文件。分片路由复杂度大于收益，如需分表由应用层完成。

### D9: 表级并发控制
嵌入模式表级跨进程互斥"一写多读"；网络模式单进程 MVCC 行级并发。

### D10: nova.db 二进制元数据
独立元数据存储，DDL 原子写入/替换，保证崩溃安全。

### D11: 嵌入与网络存储统一
两种模式相同文件布局，目录可直接互用。

### D12: KV 多表
一库多 KV 表（`ENGINE=KV`），每表独立默认 TTL。采用 Bitcask 存储模型，内存仅存索引（~20B/key），值留磁盘按需读取，百万键仅占 ~20MB 内存。

### D13: MQ 消息即时序行
Flux 中 MQ 消息 = 时序表行（MessageId + Fields），统一存储模型。

### D14: Binlog 独立于 WAL
WAL 是表级物理日志（崩溃恢复），Binlog 是库级逻辑日志（复制/审计），职责正交。

### D15: Binlog 可手工删除
文件自包含无交叉依赖，删除不导致崩溃；代价是落后的从节点需全量重建。

### D16: MQ 功能融合到 NovaQueue
废弃 StreamManager 中间层，消费组管理、延迟消息、死信队列、阻塞读取等 Stream/MQ 语义全部融合到 `NovaQueue<T>`。NovaQueue 直接持有 FluxEngine，减少一层间接调用，简化依赖链。

### D17: NovaClientFactory 统一入口
`NovaClientFactory` 作为四大场景（关系型、时序、MQ、KV）的统一入口。一个连接字符串对应一个数据库，数据库内可包含多张关系表、多张时序表（即多个 MQ topic）、多个 KV 库。嵌入模式下通过 `EmbeddedDatabase` 共用引擎实例，网络模式下通过 `NovaClientPool` 共用连接池。四大场景共用同一个 `NovaClient`，避免为不同场景建立独立连接。

### D18: 数据语义固定区域性，文本随语言变化
异常与日志文本跟随 `Localization.Culture` 翻译，但**数据语义**（SQL 数值/日期字面量与格式化、标识符与关键字大小写、文件名与分区键）一律使用 `CultureInfo.InvariantCulture` / `*Invariant` 方法。理由：进程区域性属于部署环境，不应影响存储与协议语义——de-DE 会把 `2.5` 解析成 `25`，tr-TR 会把 `Int32` 小写成 `ınt32`，非公历区域性会改变 `yyyyMMdd` 分区键。代价是 SQL `UPPER/LOWER` 等函数不做语言相关大小写折叠（与多数数据库的 ASCII 折叠行为一致）。回归测试见 `XUnitTest/Localization/CultureInvariantTests.cs` 与 AOT 冒烟；规范见 `Doc/多语言本地化.md` §3.1。

### D19: JSON 序列化宿主按运行时能力选择
`NovaJsonEncoder` 在 net8.0+ 直接引用 `SystemJson` 而非按类型名反射查找：`System.Text.Json` 反射序列化可用时用 `SystemJson`，NativeAOT（`JsonSerializer.IsReflectionEnabledByDefault=false`）下保留带裁剪注解的 `FastJson`，由调用方用 `DynamicallyAccessedMembers` 保留被序列化类型成员。理由：字符串类型查找在裁剪后可能静默失败，行为不可预测；直接引用让 AOT 路径确定且可被分析器验证。

### D20: 单文件可移除，按文件角色分级降级

- **决策**：所有长生命周期文件以 `FileShare.Read | FileShare.Delete` 打开；引擎按巡检间隔（`DbOptions.FileWatchIntervalMs`，默认 200ms）检查文件是否还在原路径。
- **语义**：二级索引 `.hidx` 缺失 → 注销索引、查询回退全表扫描、重启自动重建；主键索引 `.hidx`/`.oidx` 缺失 → 立即按行日志整表重建；行数据 `.rlog` 缺失 → 该表视为空表并重置全部索引；`.wal` 缺失 → 重建文件。
- **理由**：用户把"磁盘吃紧时按文件粒度清理"作为硬需求；MMF 哈希字典与行日志已经做到索引与载荷都不常驻托管堆，缺的只是运行期容错。
- **代价**：主键索引重建期间该表阻塞；检测窗口内（默认 ≤200ms）的写入可能落到已被移走的文件而丢失；二级索引降级期间唯一约束不生效。可配置巡检间隔为 0 换取即时检测。
- **被否决**：① 重写为 B+ 树索引——实现量大，且不解决运维删文件的问题；② 文件缺失即让整库只读——与"继续工作"的要求相反；③ 只支持重启后重建——运维无法在线释放磁盘。
- **Windows 差异**：存在映射视图时 `DeleteFile` 被拒（ERROR_USER_MAPPED_FILE），但带 `FileShare.Delete` 的句柄允许改名移走；引擎检测到路径消失后释放句柄，被移走的文件才可被真正删除。

### D21: MySQL 方言兼容优先于自定义语义
ORM（FreeSql/XCode）按 MySQL 方言发射 SQL，Nova 只需在词法与执行层补齐形状即可零补丁接入，因此新增/调整以下语义：

| 项 | 取舍 | 影响面 |
|---|---|---|
| `LIMIT m,n` | 解析为 `Offset=m, Limit=n` | 无（新增语法） |
| `` `库`.`表` `` / `.表` | 单库模型丢弃库名；`_sys.`、`information_schema.` 前缀保留 | 无（原先直接报错） |
| `BIT` | 等同 `BOOL` | 无（新增别名） |
| `bool列 = 0/1`、`CAST(x AS BOOL)` | 布尔按 0/1 参与数值比较与转换 | 原有 `bool列 = '1'` 等字符串比较从"恒不等"变为正确匹配，属修复 |
| 反斜杠转义 | 只还原标准序列（`\\ \' \" \n \r \t \0 \b \Z`），`\%`/`\_` 留给 LIKE，**未知转义原样保留** | 与 MySQL 不同：`'C:\temp'` 仍会变成制表符（`\t` 是标准序列），但 `'C:\data\path'` 不会被吞掉反斜杠。选择"安全混合"而非 MySQL 全量语义，避免存量路径字面量静默损坏 |
| `LENGTH` | 改为 UTF-8 字节数，新增 `CHAR_LENGTH` 取字符数 | **破坏性**：存量按字符数使用的查询结果会变大（中文 ×3） |
| `CONCAT` | 任一参数 NULL → NULL | **破坏性**：原先 NULL 当作空串拼接 |
| `FOR UPDATE` / `FOR SHARE` / `LOCK IN SHARE MODE` | 只识别语法，不加锁 | 依赖悲观锁的并发流程需自行加应用层锁 |
| `CHANGE COLUMN` / `RENAME TABLE` | 补齐 DDL；改名按文件组整体搬迁（data/idx/wal/rlog/schema） | 无（原先直接报错） |
| `information_schema.columns.EXTRA` | 自增列输出 `auto_increment` | 无（原恒空，CodeFirst 反向工程会误判） |
| 系统视图聚合 | `information_schema.*` 与 `_sys.*` 支持 COUNT/SUM 等聚合 | 无（原报"聚合函数不允许在此上下文中使用"，ORM 存在性检查走 SQL 时必踩） |
| CREATE TABLE 内联索引 | 支持 `UNIQUE KEY` / `KEY` / `INDEX`，未命名取首列名 | 无（原先需拆成独立 `CREATE INDEX`，FreeSql 分支专门打补丁剥离） |
| 建表列修饰符 | 接受 `UNSIGNED`/`ZEROFILL`/`CHARACTER SET`/`COLLATE`/`ON UPDATE` 但忽略语义，列级 `UNIQUE` 转唯一索引 | 无（原先直接语法报错；无符号范围与自动更新时间需应用层保证） |
| 复合主键 / 外键 | 保持不支持，但给出明确 `NotSupported` 提示 | 无（原先是含糊的语法错误，迁移时难定位） |

### D22: 类型名一套规范名，别名只做输入；长度是真约束
- 10 个规范名（`BOOL/INT/BIGINT/DOUBLE/DECIMAL/DATETIME/STRING/BINARY/GEOPOINT/VECTOR`）由 `Core/DataTypeName.cs` 的 `DataTypeNames` 统一维护，`TryParse` 认别名、`GetName`/`Format` 只吐规范名；SHOW COLUMNS、`information_schema`、`_sys.columns`、`GetDataTypeName`、`GetSchema("DataTypes")` 全部走同一张表。理由：改动前同一张表存在四套类型名（枚举名 `int32`、MySQL 兼容名 `int(11)`、CLR 名 `Int32`、GetSchema 清单），互相打架且长度是编的。
- 删除 BLOB 作为独立类型：`BINARY(n)`/`VARBINARY`/`BLOB` 在磁盘上是同一份编码（null 标记 + 4 字节长度 + 原始字节），BLOB 没有"大对象单独存"的行为，只保留 `BINARY`，其余降为别名；`BINARY(n)` 不补零。
- `STRING(n)`/`BINARY(n)`/`VECTOR(n)` 的 n 进入 schema 并参与写入校验（字符数/字节数/维度），存储仍是变长编码。理由：原实现解析完括号就丢弃，`MODIFY COLUMN ... STRING(200)` 静默无效；"长度用于索引优化"的理由也不成立（索引按全值比较）。
- **影响面 / 回退损失**：`information_schema.columns.COLUMN_TYPE` 改为规范名后，XCode 的 NovaDb 提供者必须认识新名字（`XCode/DataAccessLayer/Database/NovaDb.cs` 的 `_DataTypes` 已追加），因此 **XCode 需先发版或同批发版**，否则反向工程读不出字段类型；超长写入由"静默通过"变为 `ConstraintViolation`；旧 DDL 与旧 dump 依赖别名仍可重放。

### D23: 索引成批刷盘，崩溃后按行日志重建

- **决策**：主键与二级索引在提交时只推进内存中的已应用偏移，持久化偏移按 `DbOptions.IndexFlushIntervalMs`（默认 1000ms）成批前进，关闭时强制刷盘；周期刷盘只落元数据（`MmfRegion.Flush(syncView: false)`），强制回写整个映射视图留给关闭与压缩。
- **理由**：`FlushViewOfFile` 每次提交要花约百微秒，且视图越大越贵——数百 MB 的索引文件上每次强制回写要 100~700ms。索引是行日志的派生数据，重新落盘不产生新信息。实测单行插入 367µs → 28µs、更新 474µs → 73µs；连续批量写入再从 6.5 万行/s 提到 12 万行/s。
- **正确性**：`AppliedOffset` 只在刷盘时与节点一起持久化，因此崩溃后持久化偏移必然落后于（或等于）已落盘状态；启动时偏移与行日志不一致即整表重建。断电场景下损坏的 run 头/CRC 校验失败同样走重建。
- **代价**：崩溃后需要重建最近一个刷盘周期内的索引增量（可在 `IndexFlushIntervalMs=0` 时退化为每次提交刷盘）。
- **被否决**：① 保持每次提交刷盘——写入吞吐低一个数量级；② 完全后台异步刷盘——需要额外线程与生命周期管理，收益与「间隔触发」接近。

### D24: 有序段按体量分层合并，垃圾过半才全量回收

- **决策**：有序索引 run 数超过 12 时，只在同一量级里挑最小的 4 个 run 归并成新 run 并追加到文件尾部；新 run 先登记进 run 索引与元数据，再把旧 run 槽位清零标记失效，失效槽位进空闲列表复用；垃圾空间超过 `max(8MB, 存活字节) × 3` 时才做一次全量重写（丢弃旧版本与已删除条目）。
- **理由**：原先 run 数超限就归并重写整个文件，重写量与表规模成正比，200 万行规模单次停顿 1.8~7.3 秒，且反复触发形成 O(N²)。分层合并让单次重写量与层内规模成正比，每个条目被重写的次数与层数同阶（对数级）。
- **正确性**：任何崩溃点都能从元数据引用的 run 里读回全部条目——要么旧 run 仍在索引里，要么新 run 已被元数据引用；最坏只是同一批条目被合并两次（归并按「键 + 创建事务」去重）。全量重写走临时文件 + 原子替换。
- **代价**：文件空间放大（最多约 4 倍存活数据），读路径要归并更多 run（≤12 个游标）。
- **被否决**：① 后台线程压缩——引入并发生命周期与锁设计，收益与「增量合并」重叠；② 每次全量重写——秒级停顿不可接受。

### D25: 哈希索引扩容原地重链

- **决策**：`.hidx` 载重超过 0.75 需要扩容时，追加新桶数组后直接在旧节点上改 `NextKey` 指针完成重链；重链按分块迁移推进（每次写入最多 32768 个键节点），迁移期间新旧桶表并存，查询按「旧桶下标是否小于游标」决定查哪张表。
- **理由**：原先逐键复制节点并分配键数组，300 万键扩容要 0.9 秒以上，且旧节点全部变成死区让文件翻倍；随后改成一次性原地重链仍有 0.9 秒的提交停顿。分块迁移把这段开销摊到几十次提交上，连续批量写入的最大停顿从 870ms 降到 250ms 以内。
- **正确性**：新桶表清零并落元数据之后才开始迁移；每个键只在一张桶表里，中途崩溃时元数据仍一致，下次写入继续迁移（元数据校验会拒绝不自洽的迁移状态）。
- **代价**：迁移期间多维护一张旧桶表（内存映射，不额外占托管堆），`Enumerate` 等全量遍历要同时走两张表。

### D26: 二级索引崩溃恢复走整表重建，不做增量回放

- **决策**：启动时只有「`.hidx` 偏移对齐」和「`.idx` 基线可用且增量已清空」两种快速路径；只要还有 `.idxl` 增量，就直接从主键索引全表重建，并清空增量。
- **理由**：增量回放要让每条记录都沿值链去重，低基数列（状态、类型）单条链可达上万个主键，百万行表实测回放要 7 分钟以上；全表重建是 O(N)，91 万行实测 4.7 秒。
- **正确性**：两条路径的结果都来自已提交的行日志，语义等价；重建前清空增量避免下次启动继续背负陈旧记录。
- **代价**：崩溃后需要重读一遍行日志（与表大小线性相关），换来的是恢复时间可预期。

### D27: 取消表级 WAL，行日志即重做日志

- **决策**：表引擎不再创建/写入 `{表}.wal`；`WalMode` 保留为行日志落盘档位：`Full` 每次提交 `Flush(true)`、`Normal` 每次提交 `Flush()`、`None` 不额外 flush。`WalWriter`/`WalRecovery` 仍作为通用组件保留在库中，副本集复制另用自己的 WAL 流。
- **理由**：此前的 WAL 只写不重放（`WalRecovery` 无调用点），属于纯写放大；逐行记录还要多一次序列化与 append，Full 模式更因此每次提交做两次 fsync。移除后 Full 模式单行提交 2.2ms → 1.09ms，Normal 批量导入少一次 append/行。
- **正确性**：`.rlog` 是唯一事实源，重启即按行日志恢复数据、索引按行日志重建（见 D26）；Full 模式的持久性由行日志 fsync 保证，语义与改动前一致而不依赖未实现的回放。
- **代价**：单行事务在 Full 模式要两次 fsync（WAL + 行日志，Windows 实测约 2.2ms/次），需要更高吞吐应改用 Normal；WAL 回放尚未实现，长期可省掉这次冗余 fsync。
